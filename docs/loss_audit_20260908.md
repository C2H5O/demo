# Highlight / smoothness 审计与处理记录

## 结论

当前日志不支持“高光和 smoothness 已趋于零、没有参与优化”的判断。
两项的标量占比很小，但保持非零，而且占比总体上升。不能用标量占比
推断梯度占比，更不能直接判断对最终深度精度是否有效。

PC-Depth 的高光项是 `(1 - dot(normal, point_to_camera_direction))^2`，
鼓励法线朝向相机。表面切平面因此倾向于与观察方向垂直；**法线本身
倾向于与观察方向平行**。它是有限的软惩罚，不是必须满足的硬约束。
本次按用户条件保留现有高光公式，不增加角度阈值或无惩罚角度区间。

依据：[PC-Depth 官方实现](https://github.com/DpEstimation/PC-Depth/blob/main/losses/lightaligh.py)
的 `cal_highlight_loss`、`Depth2Normal.getNormalFrom3D`；以及
[AAAI 2025 论文](https://ojs.aaai.org/index.php/AAAI/article/download/32521/34676)。
本机对照目录为 `D:/Projects/PC-Depth-main/PC-Depth-main/`。

## 代码判断

- 高光项在有效高光像素上取均值，而非除以整幅图像面积。不能把标量小
  归因于“高光面积小导致全图平均稀释”。
- 当前系数 `lambda_highlight=0.01` 把约 0.036 的原始项压到 0.00036。
  对约 0.0955 的总 loss，它自然只有约 0.377%。
- 高光罚函数在小角度处满足 `(1-cos(theta))^2 ≈ theta^4/4`，已相当
  宽松。再加角度容忍区会进一步减弱此项，不能解决标量占比小的问题。
- Smoothness 对每帧均值归一化的逆深度计算相邻像素差，再做 RGB
  边缘加权，排除高光边。448×560 下相邻像素差可自然处于 1e-3 量级。
  乘以 0.1 后约 1.2e-4，并不表示梯度断开。
- 项目的 smoothness 是有效横纵边的合并均值；PC-Depth 原实现使用
  两个方向均值之和，且代码直接传入预测 depth。项目并非其逐行复现，
  不能直接照搬 PC-Depth 的权重。本次没有更换 smoothness 的定义。
- 当前法线归一化有 `eps=1e-6` 的面积向量下限。极小深度/退化网格
  可能产生长度小于 1 的法线；这通常增大高光罚项，不能解释 loss 消失。
  本次增加显式诊断，不在没有真实数据证据时修改原函数。

## 后续实验与证据边界

先继续原 B 的完整评估，保存空间指标、TAE、固定序列可视化与新的 mask
诊断。对照增权实验只改变高光系数，并保持初始化、数据顺序、训练预算
和评估协议一致；不要同时改 smooth 或 attention。

增权的接受条件应是有效高光区域深度/法线或重投影质量改善，同时整体
空间指标和 TAE 不退化，而不是某项 loss 占比达到某个百分数。若要在 A
和 B 之间归因 attention 的贡献，两者也必须使用相同的高光权重。

本次没有启动正式训练，也没有获得训练 checkpoint 的新精度结果。
完整测试集 110 项通过。解析面测试验证软法线罚项、独立反向、系数与
梯度线性关系以及平滑项的尺度不变性。

真实 DA3-Small + 初始 LoRA 的独立反向测试使用合成 RGB、两帧输入、
eval 模式下启用 autograd，并通过 `GradScaler.scale(loss).backward()`
